# راهنمای `.env` و داکر

PackageBuilder موقعِ نصب، رمزِ هر سرویس را از تو می‌پرسد و خودش در `.env`
و فایلِ compose می‌نشاندش. این سند می‌گوید آن مقدارها چه هستند، کجا زندگی
می‌کنند، و بعدش با کانتینرها چه کار کنی — از «داکر اصلاً چیست» تا وصل‌شدن با
DBeaver و عوض‌کردنِ رمز بی از دست دادنِ داده.

## بخش ۱ — کدام مقدارها را باید پر کنم

`.env.example` **نقشه** است، نه خودِ متغیرها. کامیت می‌شود و هیچ مقدارِ واقعی
داخلش نیست. تو از رویش یک `.env` می‌سازی — که در `.gitignore` هست و کامیت
نمی‌شود.

### در `.env` هیچ‌چیز برای پر کردن نمانده

ابزار موقعِ نصب، رمزِ هر سرویس را **از تو می‌پرسد** — با یک مقدارِ تصادفیِ
آماده که می‌توانی همان را قبول کنی یا عوضش کنی. همان مقدار در `.env` می‌نشیند
و فایلِ compose هم از همان‌جا می‌خواندش.

پس اگر پروژه را با نسخهٔ فعلیِ PackageBuilder ساخته‌ای، `.env` کامل است و
کاری ندارد.

`change-me` را فقط در `.env.example` می‌بینی — و آنجا **باید** جای‌نگه‌دار
بماند، چون آن فایل کامیت می‌شود.

### اگر پروژه‌ات قدیمی است و `change-me` در `.env` داری

| کلید | چه بگذاری |
|---|---|
| `DATABASE_URL` | فقط قسمتِ `change-me` داخلِ URL |
| `MEILI_MASTER_KEY` | کلیدِ تصادفی، حداقل ۱۶ کاراکتر |
| `MINIO_ROOT_USER` | `app` |
| `MINIO_ROOT_PASSWORD` | حداقل ۸ کاراکتر (الزامِ خودِ MinIO) |
| `GRAFANA_ADMIN_PASSWORD` | رمزِ خودت |

و اگر رمزی را در `.env` عوض می‌کنی، در `DATABASE_URL` هم همان را بگذار — دو
جا نوشته شده و باید یکی باشند.

### آن‌هایی که باید دست‌نخورده بمانند

| کلید | چرا دست نزنی |
|---|---|
| `POSTGRES_PORT`, `REDIS_PORT`, `MEILI_PORT`, `MINIO_PORT` | ابزار پورتِ **آزاد** را پیدا کرده تا با چیزی که از قبل روی سیستمت اجراست تصادم نکند. برای همین اعدادِ عجیبی مثل `5436` یا `6383` می‌بینی، نه `5432`. |
| `NEXT_PUBLIC_API_URL`, `MEILI_URL`, `MINIO_ENDPOINT` | خودشان از همان پورت‌ها ساخته شده‌اند. |
| `APP_NAME`, `APP_ENV` | درست هستند. |

### ساختنِ رمزِ تصادفی

```bash
node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
```

`base64url` عمدی است: کاراکترِ خاصی تولید نمی‌کند که داخلِ URL یا YAML دردسر شود.

> **نکته:** رمزی که داخلِ `DATABASE_URL` می‌گذاری نباید `@` یا `:` یا `/` داشته
> باشد، وگرنه ساختارِ URL می‌شکند.

## بخش ۲ — رمزها از کجا می‌آیند

موقعِ نصبِ هر سرویسی که رمز لازم دارد، پنجره‌ای باز می‌شود و رمز را می‌پرسد.
مقدارِ پیش‌فرض تصادفی است؛ می‌توانی قبولش کنی یا مالِ خودت را بنویسی.

بعدش این اتفاق می‌افتد:

```
.env                          →  مقدارِ واقعی. کامیت نمی‌شود.
deployment/docker-compose.yml →  ${POSTGRES_PASSWORD} — ارجاع، نه مقدار
.env.example                  →  change-me — جای‌نگه‌دار. کامیت می‌شود.
```

نکتهٔ مهم: فایلِ compose رمز را **در خودش ندارد**، فقط به `.env` ارجاع می‌دهد.
پس یک جا بیشتر برای عوض‌کردن وجود ندارد و نمی‌شود این دو را ناهماهنگ کرد.

> این قبلاً این‌طور نبود. در نسخه‌های قبل رمز هم در `.env` بود هم داخلِ
> `docker-compose.yml`، و اگر فقط یکی را عوض می‌کردی کانتینر سالم بالا می‌آمد
> ولی برنامه با `FATAL: password authentication failed` رد می‌شد.

### رمزی که یک‌بار انتخاب شد، عوض نمی‌شود

اگر همان تکنولوژی را دوباره نصب کنی، ابزار **مقدارِ موجودِ `.env` را نگه
می‌دارد** و رمزِ نو نمی‌سازد — حتی اگر در پنجره چیزِ دیگری بنویسی.

چرا: کانتینر با رمزِ اول ساخته شده و آن رمز داخلِ volume ثبت است. ساختنِ رمزِ
نو یعنی دیتابیسی که دیگر باز نمی‌شود.

برای عوض‌کردنِ عمدیِ رمز → [بخش ۶](#بخش-۶--عوض‌کردن-رمز-وقتی-داده-داری).

### دام: رمز فقط بارِ اول اعمال می‌شود

`POSTGRES_PASSWORD` را ایمیجِ Postgres **فقط هنگامِ ساختِ اولیه** روی یک پوشهٔ
دادهٔ خالی می‌خواند. اگر volume از قبل باشد، عوض‌کردنِ `.env` هیچ اثری ندارد.

دو راه داری:

- **داده ندارم** → بخش ۳
- **داده دارم** → بخش ۶

مطمئن نیستی کدام؟ بخش ۷ جوابش را می‌دهد.

## بخش ۳ — قدم‌به‌قدمِ راه‌اندازی

مسیرِ پروژهٔ نو، یا پروژه‌ای که داده‌اش برایت مهم نیست.

> ### ⚠️ `--env-file .env` را هرگز جا نینداز
>
> در همهٔ فرمان‌های این سند این تکه هست. حذفش خطای گمراه‌کننده می‌دهد.
>
> **چرا:** فایلِ compose پورت‌ها را این‌طور می‌نویسد:
>
> ```yaml
> ports:
>   - "${REDIS_PORT:-6379}:6379"
> ```
>
> و `docker compose` متغیرها را از پوشهٔ **فایلِ compose** می‌خواند، یعنی
> `deployment/`. آنجا `.env` نیست — `.env` در ریشهٔ پروژه است. پس بدونِ
> `--env-file`، همهٔ متغیرها به پیش‌فرضِ بعدِ `:-` می‌افتند: `6379`, `5432`,
> `7700`, `9000`. یعنی همان پورت‌های استاندارد که احتمالاً پروژهٔ دیگری
> گرفته‌شان، و می‌بینی:
>
> ```
> Error response from daemon: Bind for 0.0.0.0:6379 failed: port is already allocated
> ```
>
> این خطا **ربطی به رمز و کانفیگ ندارد** — فقط یعنی `.env` خوانده نشده.

### ۱. `.env` را بساز

```bash
copy .env.example .env
```

### ۲. اگر `change-me` مانده، پرش کن

پروژه‌ای که با نسخهٔ فعلی ساخته شده، `.env`‌اش کامل است. فقط پروژه‌های قدیمی
جدولِ بخش ۱ را لازم دارند.

### ۳. اگر قبلاً بالا آورده بودی، volume را دور بریز

```bash
docker compose --env-file .env -f deployment/docker-compose.yml down -v
```

اینجا `-v` عمدی است — دادهٔ قدیمی می‌رود تا رمزِ جدید هنگامِ ساختِ اولیه اعمال شود.
اگر تا حالا اصلاً بالا نیاورده‌ای، این قدم را رد کن.

### ۴. بالا بیاور

```bash
docker compose --env-file .env -f deployment/docker-compose.yml up -d
```

### ۵. بررسی کن

```bash
docker compose --env-file .env -f deployment/docker-compose.yml ps
```

هر سرویس باید `running` باشد. اگر یکی `restarting` بود، لاگش را ببین:

```bash
docker compose --env-file .env -f deployment/docker-compose.yml logs postgres
```

## بخش ۴ — داکر یعنی چه

### تشبیهِ کوتاه

به‌جای نصبِ Postgres روی ویندوزت، یک **کامپیوترِ کوچکِ مجازی** می‌گیری که Postgres
از قبل داخلش نصب و تنظیم شده. به آن «کانتینر» می‌گویند.

فایده‌اش: نسخهٔ دقیقی که پروژه لازم دارد را داری، سیستمت آلوده نمی‌شود، و با یک
فرمان کاملاً پاک می‌شود.

### سه واژه‌ای که باید بشناسی

| واژه | یعنی |
|---|---|
| **Image** | نسخهٔ آماده و فقط‌خواندنی — مثلِ فایلِ نصبِ `postgres:17-alpine` |
| **Container** | یک نمونهٔ در حالِ اجرا از آن image |
| **Volume** | فضایی که داده در آن می‌ماند و با پاک‌شدنِ کانتینر از بین نمی‌رود |

قاعدهٔ کلیدی:

> **کانتینر دور ریختنی است. volume نه.**

### دادهٔ من کجاست

نه داخلِ کانتینر، نه در پوشهٔ پروژه‌ات. در یک volumeِ نام‌دار:

```bash
docker volume ls
```

اسمش از نامِ پوشهٔ پروژه ساخته می‌شود، مثلِ `myapp_postgres_data`.

روی ویندوز، فیزیکاً داخلِ یک فایلِ دیسکِ مجازی روی درایوِ `C:` است:

```
C:\Users\<user>\AppData\Local\Docker\wsl\...\.vhdx
```

**مستقیم به آن فایل دست نزن.** فقط از راهِ داکر با آن کار کن.

پس جوابِ «روی داکر است یا روی سیستمِ من؟» → روی سیستمِ خودت، ولی داخلِ فضایی که
داکر مدیریت می‌کند. روی VPS نیست، مگر اینکه خودت آنجا اجرایش کنی.

حجمِ اشغال‌شده:

```bash
docker system df
```

### پورت‌ها چطور کار می‌کنند

در خروجیِ `docker ps` چنین چیزی می‌بینی:

```
0.0.0.0:5436->5432/tcp
```

یعنی پورتِ ۵۴۳۲ـِ **داخلِ** کانتینر به پورتِ ۵۴۳۶ روی **ویندوزت** وصل شده.

نتیجهٔ عملی: برای هر برنامه‌ای روی سیستمت، آن دیتابیس دقیقاً مثلِ یک Postgresِ
معمولیِ نصب‌شده رفتار می‌کند. فقط شمارهٔ پورت فرق دارد.

## بخش ۵ — وصل‌شدن با DBeaver

**DBeaver** رایگان است و Postgres و MySQL و MongoDB را با یک برنامه پوشش می‌دهد.

| فیلد | مقدار |
|---|---|
| Host | `127.0.0.1` |
| Port | همان که در `.env` است (مثلاً `5436`) |
| Database | `app` |
| Username | `app` |
| Password | همان رمزی که در `.env` گذاشتی |

> **Host را `127.0.0.1` بگذار، نه `localhost`.** روی ویندوز `localhost` اول به
> IPv6 (`::1`) ترجمه می‌شود و بعضی درایورها آنجا گیر می‌کنند. `127.0.0.1` این
> ابهام را ندارد.

### دیدنِ جدول‌ها

```
app → Databases → app → Schemas → public → Tables
```

اگر `Tables` خالی بود، یعنی هنوز migration یا ORM اجرا نکرده‌ای. طبیعی است.

## بخش ۶ — عوض‌کردنِ رمز وقتی داده داری

اینجا `down -v` ممنوع است. رمز را از **داخلِ خودِ دیتابیس** عوض می‌کنیم تا داده
دست‌نخورده بماند.

### ۱. اول پشتیبان بگیر

```bash
docker compose --env-file .env -f deployment/docker-compose.yml exec postgres pg_dump -U app app > backup.sql
```

### ۲. رمز را عوض کن

```bash
docker compose --env-file .env -f deployment/docker-compose.yml exec postgres psql -U app -d app -c "ALTER USER app WITH PASSWORD 'رمز-جدید';"
```

### ۳. همان رمز را در `.env` بنویس

فقط `.env` — فایلِ compose خودش از آنجا می‌خواند. اگر رمز داخلِ `DATABASE_URL`
هم هست، آنجا هم عوضش کن.

### ۴. کانتینر را دوباره بساز

```bash
docker compose --env-file .env -f deployment/docker-compose.yml up -d --force-recreate
```

`-v` نزدی، پس volume سرِ جایش است و داده نرفته.

## بخش ۷ — پشتیبان‌گیری و بازگردانی

### گرفتن

```bash
docker compose --env-file .env -f deployment/docker-compose.yml exec postgres pg_dump -U app app > backup.sql
```

### فهمیدنِ اینکه اصلاً داده‌ای داری یا نه

`backup.sql` را باز کن. اگر فقط این‌ها را دیدی:

```sql
--
-- PostgreSQL database dump
--

SET statement_timeout = 0;
...
--
-- PostgreSQL database dump complete
--
```

یعنی **دیتابیس کاملاً خالی است** — نه جدولی، نه سطری. آن‌وقت خیالت راحت است و
می‌توانی مسیرِ سادهٔ بخش ۳ را بروی.

اگر `CREATE TABLE` و `INSERT` و `COPY` دیدی، یعنی داده داری. اندازهٔ فایل هم
گویاست: چند صد بایت یعنی خالی؛ چند کیلوبایت یا بیشتر یعنی پر.

### برگرداندن

```bash
docker compose --env-file .env -f deployment/docker-compose.yml exec -T postgres psql -U app -d app < backup.sql
```

آن `-T` لازم است: بدونش داکر یک TTY می‌سازد و ورودیِ فایل به فرمان نمی‌رسد.

## بخش ۸ — فرمان‌های روزمرهٔ داکر

همه از ریشهٔ پروژه اجرا می‌شوند.

**وضعیت**

```bash
docker compose --env-file .env -f deployment/docker-compose.yml ps
```

**لاگِ زنده**

```bash
docker compose --env-file .env -f deployment/docker-compose.yml logs -f postgres
```

**خواباندن بدونِ حذفِ داده** — برای وقتی که روی پروژه کار نمی‌کنی و نمی‌خواهی رم
مصرف شود. با `up -d` برمی‌گردد.

```bash
docker compose --env-file .env -f deployment/docker-compose.yml stop
```

**بالا آوردن**

```bash
docker compose --env-file .env -f deployment/docker-compose.yml up -d
```

**خطِ فرمانِ دیتابیس**

```bash
docker compose --env-file .env -f deployment/docker-compose.yml exec postgres psql -U app -d app
```

**دیدنِ همهٔ کانتینرهای سیستم**

```bash
docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Ports}}\t{{.Status}}"
```

### ⚠️ تنها فرمانی که داده را نابود می‌کند

```bash
docker compose --env-file .env -f deployment/docker-compose.yml down -v
```

آن `-v` است که volume را پاک می‌کند. `down` بدونِ `-v` فقط کانتینرها را برمی‌دارد
و داده می‌ماند. **`-v` را هرگز اتفاقی نزن.**

## بخش ۹ — رفعِ خطاهای رایج

### `FATAL: password authentication failed for user "app"`

به ترتیب بررسی کن:

**۱. رمز واقعاً چیست؟** از داخلِ خودِ کانتینر تست کن:

```bash
docker exec -e PGPASSWORD=رمزت نام-کانتینر psql -h 127.0.0.1 -U app -d app -c "select 1;"
```

اگر اینجا جواب داد، دیتابیس سالم است و مشکل از تنظیمِ کلاینت است.

**۲. رمزِ کش‌شدهٔ DBeaver.** فیلدِ Password را کاملاً خالی کن و دستی تایپ کن —
کپی/پیست گاهی فاصلهٔ اضافه می‌آورد و DBeaver هم رمزِ قدیمی را نگه می‌دارد.

**۳. رمزِ داخلِ volume قدیمی است.** `.env` را عوض کرده‌ای ولی volume از قبل با
رمزِ قبلی ساخته شده. → بخش ۲، «رمز فقط بارِ اول اعمال می‌شود».

### پورت اشغال است

```
Error response from daemon: Bind for 0.0.0.0:6379 failed: port is already allocated
```

**اول از همه:** ببین `--env-file .env` را در فرمان گذاشته‌ای یا نه. اگر پورتی که
در خطا آمده یک عددِ **استاندارد** است (`6379`, `5432`, `7700`, `9000`) ولی در
`.env` عددِ دیگری نوشته‌ای، علتش همین است و نه چیزِ دیگر. → بخش ۳، کادرِ هشدار.

اگر واقعاً پورتِ خودت اشغال است، ببین چه چیزی رویش نشسته:

```bash
docker ps --format "{{.Names}}\t{{.Ports}}"
```

در `.env` پورت را به عددِ آزادی عوض کن، و مطمئن شو URLهایی که همان پورت را دارند
(`DATABASE_URL`, `MEILI_URL`, …) هم به‌روز شوند.

### کانتینر مدام `restarting` است

```bash
docker compose --env-file .env -f deployment/docker-compose.yml logs نام-سرویس
```

شایع‌ترین علت‌ها: `POSTGRES_PASSWORD` خالی است، یا `MINIO_ROOT_PASSWORD` کمتر از
۸ کاراکتر است.

### از Node وصل نمی‌شود ولی از DBeaver می‌شود

در URLهای سمتِ سرور `127.0.0.1` بنویس، نه `localhost`. Node روی ویندوز
`localhost` را اول به IPv6 ترجمه می‌کند و به port mappingِ داکر نمی‌رسد.

---

## خلاصهٔ یک‌نگاهی

| کِی | چه کن |
|---|---|
| پروژهٔ نو | ابزار رمز را پرسیده و `.env` را پر کرده ← فقط `up -d` |
| رمز عوض شد، داده ندارم | `down -v` بعد `up -d` |
| رمز عوض شد، داده دارم | `pg_dump` ← `ALTER USER` ← فایل‌ها ← `up -d --force-recreate` |
| خطای authentication | اول از داخلِ کانتینر تست کن، بعد سراغِ کلاینت برو |
| کارم تمام شد | `stop` — نه `down -v` |
| هر فرمانِ docker compose | `--env-file .env` را جا نینداز |
