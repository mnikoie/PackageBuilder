# ۰۰۰۲ — استکِ خودِ ابزار

- **تاریخ:** ۱۴۰۵/۰۵/۲۷
- **وضعیت:** ⏳ **پیشنهادی — منتظرِ تأیید**

> این سند دربارهٔ تکنولوژیِ **خودِ PackageBuilder** است، نه پروژه‌هایی که
> می‌سازد. آن‌ها هرکدام استکِ خودشان را دارند.
>
> تا وقتی این تصمیم تأیید نشود، `package.json` ساخته نمی‌شود — همان قاعدهٔ
> شمارهٔ ۳ که برای پروژه‌های تولیدی گذاشتیم، برای خودمان هم اجرا می‌شود.

## زمینه

ابزار باید سه کارِ سخت را انجام دهد که انتخاب را تقریباً تعیین می‌کنند:

1. یک **PowerShell 7 واقعیِ همیشه‌زنده** را در صفحه نشان دهد (نه لاگِ
   شبیه‌سازی‌شده) — با رنگ، نوارِ پیشرفت، و ورودیِ کاربر.
2. **فایل‌سیستم و Docker** را واقعاً بخواند.
3. **لوکال** اجرا شود، روی ویندوز، بدونِ نیاز به سرورِ بیرونی.

## پیشنهاد

| بخش | انتخاب | دلیل |
|---|---|---|
| رانتایم | Node.js | `node-pty` تنها راهِ عملیِ داشتنِ یک PTYِ واقعیِ ویندوزی است |
| ترمینالِ سمتِ سرور | `node-pty` | در نسخهٔ قبلی روی همین ویندوز جواب داد، باینریِ آماده دارد و نیازی به کامپایل ندارد |
| ترمینالِ سمتِ مرورگر | `xterm.js` + `addon-fit` | همان چیزی که VS Code استفاده می‌کند |
| پُلِ بین دو طرف | WebSocket (`ws`) | خروجیِ ترمینال جریانی است، درخواست/پاسخ جواب نمی‌دهد |
| سرورِ HTTP | خودِ `node:http` | چند مسیرِ ساده است؛ فریم‌ورک فقط وابستگی اضافه می‌کند |
| رابطِ کاربری | HTML/CSS/JSِ ساده، بدونِ مرحلهٔ بیلد | ابزارِ لوکالِ تک‌کاربره است؛ بیلد یعنی هر تغییر کوچک، یک چرخهٔ کامپایل |
| تست | Playwright | تصمیمِ خودت: یک‌بار تستِ سرتاسری بنویس، جای چک‌کردنِ دستیِ مرورگر |

جمعاً چهار وابستگیِ اصلی: `node-pty`, `ws`, `@xterm/xterm`, `@xterm/addon-fit`
(به‌علاوهٔ `@playwright/test` برای تست).

## گزینه‌های دیگر

| گزینه | مزیت | چرا پیشنهاد نمی‌شود |
|---|---|---|
| Python + FastAPI | برای اسکریپتِ فایل‌سیستم راحت‌تر | معادلِ خوبِ `node-pty` برای PTYِ ویندوزی ندارد — همان مشکلِ اصلی حل نمی‌شود |
| اپلیکیشنِ Electron/Tauri | ظاهرِ برنامهٔ بومی | حجم و پیچیدگیِ بیلد، بی‌دلیل برای ابزارِ لوکال |
| React/Vue برای UI | ساختارِ بهترِ UI | مرحلهٔ بیلد اضافه می‌کند؛ اگر UI بزرگ شد، بعداً قابلِ مهاجرت است |
| فقط CLI، بدونِ مرورگر | ساده‌ترین | دیدنِ همزمانِ وضعیت و ترمینال و گزینه‌ها، نصفِ ارزشِ کار است |

## پیامدها

- ابزار خودش Node لازم دارد، حتی اگر پروژه‌ای که می‌سازد پایتونی باشد. قابلِ
  قبول است: ابزار جدا از محصول است.
- بدونِ مرحلهٔ بیلد، تغییرِ UI فوری دیده می‌شود؛ در عوض TypeScript و
  type-checkingِ سمتِ UI را از دست می‌دهیم. برای ابزارِ لوکال معاملهٔ خوبی است.
- منطقِ اصلی (قدم‌های ۲ و ۳ و ۵) عمداً از UI جدا نوشته می‌شود، تا اگر روزی
  UI عوض شد، منطق دست‌نخورده بماند.

## پرسشِ باز برای تأیید

اگر ترجیح می‌دهی ابزار **پایتونی** باشد یا **رابطِ کاربری با یک فریم‌ورک**
نوشته شود، همین‌جا بگو — چون بعد از قدمِ ۴ برگشتن از این تصمیم گران می‌شود.
