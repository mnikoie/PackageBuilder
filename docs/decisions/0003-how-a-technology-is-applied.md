# ۰۰۰۳ — یک تکنولوژی چطور اعمال می‌شود

- **تاریخ:** ۱۴۰۵/۰۵/۲۷
- **وضعیت:** ✅ پذیرفته‌شده (تأییدِ صریحِ کاربر در ۱۴۰۵/۰۵/۲۷)

## زمینه

قلبِ ابزار این است: کاربر یک تکنولوژی را انتخاب می‌کند، و ابزار باید آن را
**واقعاً** به پروژه اضافه کند. سه سؤال باید جواب می‌گرفت: فایل‌ها از کجا
بیایند، چقدر عمیق ساخته شود، و چطور برگشت‌پذیر باشد.

## تصمیم

### ۱. منبع: CLIِ رسمیِ خودِ تکنولوژی + یک لایهٔ نازکِ «چسب»

اسکلتِ هر تکنولوژی با CLIِ رسمیِ خودش ساخته می‌شود (`npm create vite`،
`nest new`، `npx create-react-router`، …). ما آن فایل‌ها را دست‌نویس نمی‌کنیم.

بعد از آن، یک لایهٔ کوچکِ «چسب» از خودمان اعمال می‌شود که کارِ CLIها را به هم
وصل می‌کند و هیچ‌کدامشان انجامش نمی‌دهند:

- متغیرهای env و اضافه‌کردنشان به `.env.example`
- وصل‌کردنِ app به مونوریپو (workspace، مسیرها، `tsconfig` مشترک)
- پورت‌ها و آدرس‌های داخلی، تا appها همدیگر را پیدا کنند
- ثبتِ تصمیم در `docs/decisions/` و `project.config.json`

### ۲. عمق: کدِ کارکنندهٔ قابلِ اجرا

انتخابِ یک تکنولوژی یعنی پکیج + کانفیگ + یک نمونهٔ واقعی که **بالا می‌آید**.
نه یک پوشهٔ نیمه‌کاره که خودت باید کدِ اولش را بنویسی.

با یک استثنای صادقانه: این برای پروژهٔ **نو** است. برای **تعویضِ** فریم‌ورکِ
یک پروژهٔ موجود، ابزار باید صریحاً بگوید «نمی‌توانم دکمه‌ای عوض کنم» — چون
مهاجرتِ کدِ نوشته‌شده کارِ یک دکمه نیست. ادعای خلافش، همان خطای نسخهٔ قبلی است.

### ۳. برگشت‌پذیری: هر تصمیم = یک commitِ جدا

هر پروژه از قدمِ صفر `git init` دارد. هر تصمیمی که اعمال می‌شود، یک commitِ
مستقل با پیامِ روشن می‌گیرد. برگشت از یک تصمیم می‌شود `git revert`.

این تنها راهی است که قاعدهٔ ۴ («هر کاری دو طرفه باشد») برای تغییرِ **ساختاری**
هم واقعاً اجرا شود؛ با `pnpm remove` فقط پکیج برمی‌گردد، نه کدی که نوشته شده.

## گزینه‌های دیگر

| گزینه | مزیت | چرا رد شد |
|---|---|---|
| قالبِ دست‌نویسِ خودمان | کنترلِ کاملِ هر خطِ کد | با هر نسخهٔ جدیدِ تکنولوژی‌ها کهنه می‌شود و باید دستی به‌روز شود — همان بلایی که سرِ قالبِ `25` آمد |
| فقط CLIِ رسمی، بدونِ چسب | ساده‌ترین و کم‌خطاترین | خروجی‌ها به هم وصل نمی‌شوند؛ env و پورت‌ها و مونوریپو دستی می‌ماند |
| فقط نصبِ پکیج (بدونِ کد) | سریع | ابزار می‌شود یک مدیرِ وابستگی، نه سازندهٔ پروژه |
| حذف با دستورِ معکوس (`remove`) | مستقیم‌تر | کدِ نوشته‌شده را برنمی‌گرداند؛ فقط برای پکیجِ تنها کار می‌کند |

## پیامدها

- ابزار به CLIهای بیرونی وابسته می‌شود: باید شبکه داشته باشد، و اگر یک CLI
  رفتارش را عوض کند، لایهٔ چسب باید به‌روز شود. در عوض کدِ تولیدی هیچ‌وقت کهنه
  نمی‌شود.
- خروجیِ CLIها یکسان نیست (بعضی سؤالِ تعاملی می‌پرسند). برای هرکدام باید
  حالتِ غیرتعاملی‌اش پیدا و ثبت شود — این جزوِ کارِ قدمِ ۶ است.
- لایهٔ چسب جایی است که پیچیدگیِ واقعی جمع می‌شود. باید کوچک و آزمایش‌شده
  بماند، وگرنه خودش تبدیل به همان قالبِ کهنه‌شدنی می‌شود.
